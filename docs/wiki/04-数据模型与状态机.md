# 04 数据模型与状态机

数据库为 SQLite（纯 Go 驱动），使用 GORM `AutoMigrate` 自动建表。表名遵循 GORM
默认复数蛇形命名（如 `users`、`task_steps`）。所有时间字段为 Go `time.Time`，
序列化为 RFC3339。

## 1. 实体关系

```
User 1 ─── N RecoveryCode
User 1 ─── N User（ParentID 自关联：主账号 / 子用户）

Server 1 ─── N Directory
Server 1 ─── 1 ServerMetric

Project 1 ─── N ProjectDirectory ─── N Directory
Project 1 ─── N ProjectMember ─────── N User
Project 1 ─── N Task

Task 1 ─── N TaskStep
Task N ─── 1 Server
Task N ─── 1 Directory
Task N ─── 1 Package
Task N ─── 0..1 Script（PreScript）
Task N ─── 0..1 Script（Script）

AuditLog 独立记录，按 actor_id / task_no 做逻辑关联
```

## 3. 任务状态机

### 3.1 状态流转

```
                 createTask/publish/rollback
                            │
                            ▼
                       ┌─────────┐
                       │ pending │  stage=queued
                       └────┬────┘
            排队中取消       │ 获得目录锁/服务器闸门/全局闸门
        ┌───────────────────┤
        │                   ▼
        ▼              ┌───────────┐
   ┌──────────┐        │ uploading │  stage=prepare/backup/upload
   │ canceled │        └─────┬─────┘
   └──────────┘              │ OnStage(verify)
                             ▼
                       ┌───────────┐
                       │ verifying │
                       └─────┬─────┘
                             │ OnStage(precheck/unpack/script)
                             ▼
                       ┌───────────┐
                       │ executing │
                       └─────┬─────┘
                 ┌───────────┼───────────┐
                 ▼           ▼           ▼
             ┌─────────┐ ┌────────┐ ┌──────────┐
             │ success │ │ failed │ │ canceled │
             └─────────┘ └────────┘ └──────────┘
```

说明：

- 上图为终态语义简图。由于前置校验在备份之前执行，实际状态可能出现
  `uploading → executing（precheck）→ uploading（backup/upload）→ verifying → executing`
  的短暂回跳；这是 `OnStage` 映射的当前实现行为。
- `OnStage` 的映射：`verify` → `verifying`；`precheck` / `unpack` / `script` / `done`
  → `executing`；`prepare` / `backup` / `upload` 保持 `uploading`。
- 成功时 `finishTask` 补 `progress=100`、`stage=done`。
- `pending` 阶段取消直接写 `canceled`；执行中取消通过 `context.CancelFunc`
  让执行器返回，`runTask` 根据 `ctx.Err()` 归为 `canceled`。
- 服务重启时，`RecoverInterruptedTasks` 把所有未终态任务与运行中步骤标记为
  `failed`，并写 `task.recover` 审计。

### 3.2 阶段与进度

| stage | 触发点 | progress |
|---|---|---|
| `queued` | 创建任务 | 0 |
| `prepare` | 开始执行 | 5 |
| `prepare` | `StepPrepare` | 10 |
| `precheck` | `StepPreCheck` | 15 |
| `backup` | `StepBackup` | 25 |
| `upload` | `StepUpload` | 45 |
| `verify` | `StepVerify` | 60 |
| `unpack` | `StepUnpack` | 75 |
| `script` | `StepScript` | 90 |
| `done` | 成功收尾 | 100 |

### 3.3 项目批次状态

`projectHistory` 按 `BatchNo` 聚合任务后用 `aggregateStatus` 计算：

- 任一任务未终态 → `running`
- 否则任一任务 `failed` → `failed`
- 否则全部 `success` → `success`
- 否则（存在 `canceled`）→ `canceled`

批次全部终态且全部成功时，`settleProjectBatch` 才把项目版本推进到
`tasks[0].ProjectVersion`；任一失败或取消都不推进。

### 3.2 中断恢复（`interrupted`）

`uploading` / `verifying` / `executing` 状态的任务在服务重启后进入 `interrupted`（待恢复），
运行中的步骤标记 `failed`，等待人工处置：

- `POST /tasks/:id/resume` → 回到 `pending` 重新入队；续跑时「上次已成功」的步骤自动跳过，
  校验类步骤重新执行；时间线追加 `续跑校验` 说明；`task.resume` 入审计；
- `POST /tasks/:id/mark-failed` → 归为 `failed` 收口；`task.markfailed` 入审计；
- `pending` 任务重启后自动重新入队（从未开始执行，无恢复语义）；
- 目录策略新增 `clean_replace`（干净替换）：zip 解包时按文件级差异清理包内不存在的旧文件；
  「仅新增」约束同样对 zip 生效。

## 5. 持久化与数据生命周期

- **SQLite 参数**：`busy_timeout=5000`、`journal_mode(WAL)`。
- **权限**：数据目录 `0700`，数据库文件 `0600`，包文件 `0600`。
- **迁移**：启动时 `AutoMigrate`，无版本号与回滚脚本。
- **删除行为**：
  - 删除服务器 → 同时删除其目录配置；历史任务保留（任务内已有快照）。
  - 删除目录 → 历史任务保留；执行前发现目录不存在会失败。
  - 删除脚本 → 历史任务保留；排队任务执行前发现脚本不存在会失败。
  - 删除项目 → 删除目录绑定与成员关系；历史任务保留。
  - 安装包没有删除接口，仓库文件与记录会持续累积，受 `storage.max_total_mb` 约束。
- **无自动清理**：`audit_logs`、`tasks`、`task_steps` 不会由应用自动清理；
  `task_steps.output` 为 `text`，长期运行需关注数据库体积。
- **备份含义**：部署时的 `<目录>.bak-*` 是目标机上的版本备份，不是数据库备份；
  数据库与包仓库需单独备份。
