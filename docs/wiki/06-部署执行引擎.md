# 06 部署执行引擎

本文描述从「用户点击部署」到「任务终态」的完整执行链路，以及 local / ssh 两种
执行器的行为差异、并发控制、失败语义与项目批次逻辑。

## 1. 执行抽象

核心接口与输入定义在 [deployer.go](../../server/internal/deploy/deployer.go)：

```go
type Deployer interface {
    Deploy(ctx context.Context, req Request) error
}

type Request struct {
    Server     model.Server
    Directory  model.Directory
    Package    model.Package
    PreScript  *model.Script
    Script     *model.Script
    SourcePath string   // 中控机上的包文件绝对路径
    Hooks      Hooks
}
```

可选能力通过类型断言启用：

- `Pinger`：`Ping(ctx, srv) error`，用于服务器连通性检测；
- `Prober`：`Probe(ctx, srv, dirs) (*model.ServerMetric, error)`，用于指标采集。

`Hooks` 把执行进度回传给任务记录：

| 回调 | 调用方 | 消费方 |
|---|---|---|
| `OnStep(name)` | 执行器 | 结束上一步、创建新 `task_step` |
| `OnLog(line)` | 执行器 | 追加到当前步骤 `output` |
| `OnStage(stage, pct)` | 执行器 | 更新任务 `stage/progress/status` |

## 2. 任务创建：进入执行前的校验

入口：`App.createTask`（[task_api.go](../../server/internal/api/task_api.go)）。

```
请求
 ├─ 审计员 → 403
 ├─ 服务器存在 → 否则 400
 ├─ 服务器在用户 serverScope → 否则 403
 ├─ 目录存在且 dir.ServerID == srv.ID → 否则 400
 ├─ 安装包存在 → 否则 400
 ├─ 前置脚本阶段 == precheck → 否则 400
 ├─ 后置脚本阶段 == postdeploy → 否则 400
 ├─ 服务器 env == prod → verifyStepUpOTP
 │     ├─ 未绑定 OTP / 未输入 / 校验失败 / 限流 → 401 code 1428
 │     └─ 通过 → otpVerified = true
 ├─ 单用户未终态任务数 + 1 ≤ max_pending_per_user → 否则 429 code 4001
 ├─ 创建 Task（status=pending, stage=queued）
 └─ go runTask(task.ID)
```

任务号：`D` + `YYYYMMDDHHMMSS` + 6 位随机十六进制。

任务创建时快照了服务器名、目录路径、包名、脚本名与脚本版本；执行阶段还会重新
加载实体，确保排队期间配置未被删除或篡改。

## 3. 排队与并发控制

`runTask` 的加锁顺序：

```
1. lockDirectory(task.DirectoryID)      // 同一目录串行
2. acquireServerGate(srv.ID, srv.MaxConcurrent)
3. a.Sem <- struct{}{}                  // 全局并发
4. 重新读取 task，确认仍为 pending
5. context.WithCancel + Sessions.add
6. 重新加载目录 / 包 / 脚本
7. Deployer.Deploy
```

| 控制 | 配置 | 行为 |
|---|---|---|
| 目录串行 | 无 | 同一 `directory_id` 的任务排队；避免备份/解包互相覆盖 |
| 服务器并发 | `servers.max_concurrent` | 每台服务器独立闸门；配置变化且当前空闲时重建容量 |
| 全局并发 | `deploy.max_concurrent` | 中控机整体上限，默认 3 |
| 单用户排队 | `deploy.max_pending_per_user` | 统计 `pending/uploading/verifying/executing`，默认 10 |

加锁顺序的设计目的：先等待目录锁和服务器闸门，最后才占用全局槽位，避免
「占着全局并发空等某台服务器」。

排队期间被取消：

- `pending` 任务由 `cancelTask` 直接写 `canceled`；
- `runTask` 拿到锁后重读任务，若状态不再是 `pending` 直接返回。

## 4. 执行阶段与状态回写

`runTask` 在开始执行时把任务更新为：

```text
status=uploading, stage=prepare, progress=5, started_at=now, message=开始执行
```

随后执行器按步骤调用 Hooks，`OnStep` 会：

1. 把上一个步骤标记 `success` 并写 `finished_at`；
2. 创建新步骤（`status=running`、`seq` 递增）；
3. `OnLog` 追加到当前步骤 `output`；
4. `OnStage` 更新任务阶段与进度。

步骤与任务状态映射：

| 步骤 | stage | progress | 任务状态 |
|---|---|---|---|
| 准备部署目录 | `prepare` | 10 | uploading |
| 执行前置校验 | `precheck` | 15 | executing |
| 备份现有版本 | `backup` | 25 | uploading |
| 上传安装包 | `upload` | 45 | uploading |
| 校验安装包 | `verify` | 60 | verifying |
| 解包与替换 | `unpack` | 75 | executing |
| 执行部署脚本 | `script` | 90 | executing |
| 收尾 | `done` | 100 | executing → success |

注意：前置校验步骤在备份之前执行，因此任务状态可能出现
`uploading → executing（precheck）→ uploading（backup/upload）→ verifying` 的短暂回跳；
上表按步骤顺序列出，状态列是每一步触发时的目标状态。

任务终态由 `finishTask` 写入：

- `success`：`progress=100`、`stage=done`、`message=部署完成`；
- `failed`：执行器返回错误信息；
- `canceled`：`ctx.Err() != nil` 时归为取消。

每次终态都会写一条 `task.finish` 审计；项目任务还会触发批次结算。

## 5. 本地沙箱执行器（local）

实现：[local.go](../../server/internal/deploy/local.go)

适用：本地开发、演示、前端联调。目标路径映射：

```
<storage.sandbox_root>/<server.name>/<directory.path 去掉开头 />
```

例如 `job-dev-01` + `/opt/apps/demo` → `server/data/sandbox/job-dev-01/opt/apps/demo`。

执行步骤：

1. **准备目录**：`MkdirAll`；统计目录占用，超过 `maxSizeMB` 拒绝。
2. **前置校验**：若绑定，仅渲染脚本内容并写日志，不执行。
3. **备份**：`backupBeforeDeploy=true` 且目录非空时，
   `os.Rename(target, target.bak-YYYYMMDDHHMMSS)`，再重建空目录。
4. **上传**：复制包到 `target/.incoming-<包名>`。
5. **校验**：本地计算 SHA256 与 `Package.SHA256` 比对。
6. **解包/替换**：
   - zip：`unzip` 安全解压；
   - jar 等：`AllowOverwrite=false` 且目标存在则拒绝，否则 `rename`。
7. **后置脚本**：仅渲染回显，不执行。
8. **清理备份**：只保留最近 `keepReleases` 个 `<target>.bak-*`。

本地模式**不会执行任意脚本**，这是刻意设计，避免开发机被脚本注入。

## 6. SSH 执行器（ssh）

实现：[ssh.go](../../server/internal/deploy/ssh.go)

### 6.1 连接

`dial` 流程：

1. `ResolveCredential(credentialRef)`：
   - `env:NAME` → 读取环境变量；
   - `file:/path` 或 `file:~/path` → 读取文件内容；
   - 其他形式 → 报错（数据库永不存明文）。
2. `authType=password` → `ssh.Password`；否则解析私钥 `ssh.ParsePrivateKey`。
3. 主机指纹策略：
   - 已登记 `host_key_fingerprint` → 严格比对算法与 SHA256；
   - 未登记且 `auto_trust_hostkey=true` → 首次连接自动信任，异步落库并写审计；
   - 否则 → 回退 `~/.ssh/known_hosts`；文件缺失直接拒绝；
   - 仅开发环境可 `PACKRUN_SSH_INSECURE=1` 跳过校验。
4. 连接超时 10 秒。

### 6.2 部署步骤

| 步骤 | 远程命令/行为 |
|---|---|
| 准备目录 | `mkdir -p '<target>'`；`du -sm` 检查阈值 |
| 前置校验 | 在目标目录执行 `precheck` 脚本；失败立即终止 |
| 备份 | 目录非空时 `cp -a target target.bak-<时间戳>` |
| 上传 | 流式 `cat > /tmp/packrun-<纳秒>-<安全文件名>` |
| 校验 | `sha256sum <tmp>` 与包摘要比对 |
| 解包（zip） | 条目数检查 → 路径穿越检查 → 符号链接检查 → `ulimit -f` + `unzip -o -q` → 解压后 `du` 复核 |
| 解包（jar） | `AllowOverwrite=false` 时检查存在；`mv -f` 到目标 |
| 后置脚本 | base64 传输，`timeout <n> sh -c`；`RunAs` 不同时 `sudo -n -u` |
| 清理备份 | `ls -1dt target.bak-* | tail -n +<keep+1>` 删除 |
| 收尾 | 删除 `/tmp` 临时包；进度 100 |

zip 安全检查细节：

```sh
# 条目数
unzip -Z1 <tmp> | wc -l
# 绝对路径 / ..
unzip -Z1 <tmp> | grep -Eq '(^/|\.\.)' && echo UNSAFE || echo SAFE
# 符号链接（需要 zipinfo）
command -v zipinfo >/dev/null 2>&1 || echo NOZIPINFO
zipinfo -l <tmp> | grep -Eq '^l' && echo SYMLINK || echo SAFE
# 解压时限制单文件大小
ulimit -f <maxBytes/1024>; unzip -o -q <tmp> -d <target>
```

目标机缺少 `zipinfo` 时**直接失败**，不会降级为不安全解压。

### 6.3 目标机依赖

SSH 模式要求业务服务器具备：

| 命令 | 用途 |
|---|---|
| `sh`、`mkdir`、`cp`、`mv`、`rm`、`ls`、`du`、`df`、`cat` | 基础文件操作 |
| `sha256sum` | 包校验 |
| `unzip`、`zipinfo` | zip 解包与安全审查 |
| `timeout` | 脚本超时（通常来自 coreutils） |
| `base64` | 脚本内容传输 |
| `sudo -n` | 仅当脚本 `runAs` 与 SSH 登录用户不同 |
| `nproc`、`/proc`、`hostname`、`uname` | 指标采集（缺失时字段留空） |

### 6.4 远程执行超时

`remoteExec` 默认 15 分钟；`Probe` 使用 30 秒。上下文取消或超时会向会话发送
`SIGKILL` 并返回错误。

## 7. 安全防护清单

| 风险 | 防护 | 位置 |
|---|---|---|
| 部署目录穿越 | 必须绝对路径，拒绝 `..` 和根目录 | `NormalizePath` |
| 服务器名作为目录片段 | 仅 `A-Za-z0-9._-`，拒绝 `.`/`..` | `ValidateServerName` |
| 包文件名注入 | basename + 控制字符替换 | `sanitizePackageName` / `sanitizeName` |
| 远程命令注入 | 所有路径/参数 `shellQuote`；脚本 base64 传输 | `ssh.go` |
| zip 路径穿越 | 拒绝绝对路径、`..`、越界父目录 | `unzip` / SSH `unzip -Z1` |
| 符号链接逃逸 | 本地 `EvalSymlinks` 校验；远程 `zipinfo` 拒绝 | `unzip` / `ssh.go` |
| 解压炸弹 | 条目数 ≤20000；解压字节 ≤目录阈值或 1GB；`ulimit -f` | `unpackBudget` / `checkUnpackedSize` |
| 目录被占满 | 部署前与解压后两次 `du` 阈值校验 | `local.go` / `ssh.go` |
| 包仓库占满 | 上传前预检 + 写后复核 | `package_api.go` |
| 凭据泄露 | 数据库只存引用；非管理员脱敏 | `server_api.go` |
| 中间人 | TOFU 指纹登记 + 后续严格比对 | `hostKeyCallbackFor` |
| 脚本提权 | `sudo -n`（无交互），失败即脚本失败 | `runRemoteScript` |

## 8. 项目批量发布与回滚

### 8.1 发布前置校验

`checkPublishPrerequisites`：

1. 审计员拒绝；
2. 项目可读（管理员或成员）；
3. 项目无进行中批次；
4. 已绑定至少一个目录；
5. 每个目录的服务器都在用户 `serverScope`；
6. 任一目录 `serverEnv=prod` → step-up 必须通过。

### 8.2 创建批次任务

`createBatchTasks` 为每个绑定目录创建一条任务：

- 共享 `BatchNo`（`PR` + 时间 + 随机）；
- 共享 `ProjectID`、`ProjectVersion`、`Kind`、`Remark`；
- 分别记录 `ServerID/ServerName/DirectoryID/TargetPath`；
- 每条任务独立 `go runTask`，由并发闸门调度。

发布版本：`bumpVersion(current)`，`vX.Y.Z → vX.Y.(Z+1)`；无法解析从 `v0.0.1` 起。

### 8.3 批次结算

`settleProjectBatch(projectID, batchNo)`：

1. 批次仍有非终态任务 → 返回；
2. 任一任务非 `success` → 不推进版本；
3. 全部成功 → `projects.version = tasks[0].ProjectVersion`。

因此项目版本只有「整批成功」才推进；部分失败时版本保持不变，历史仍可查看。

### 8.4 回滚

`rollbackProject`：

- 源批次必须属于当前项目；
- 当前项目版本等于源版本 → 拒绝；
- 源批次包记录与文件必须仍存在（包文件被清理则无法回滚）；
- 复用源任务绑定的脚本（若记录仍存在）；
- 创建 `kind=rollback` 的新批次任务，`remark="回滚自 <当前版本>"`；
- 批次全部成功后，项目版本回到源版本。

回滚不是「恢复目标机备份」，而是把历史安装包重新部署一遍。

## 9. 失败、取消与恢复

### 9.1 失败

- 任一步骤返回错误 → 当前步骤 `failed`，任务 `failed`，`message` 为错误信息；
- **不会自动回滚**到 `.bak-*`；备份仅保留在现场，需要人工恢复；
- 部分文件可能已写入目标目录（例如解压中途失败），任务详情日志可用于排查；
- 失败任务写 `task.finish` 审计，`result=fail`。

### 9.2 取消

- `pending`：直接 `canceled`，不进入执行；
- 执行中：`Sessions.cancel(taskID)` 触发 `context.CancelFunc`；
  - `LocalDeployer` 的 `sleep` 会响应 `ctx.Done()`；
  - SSH 的 `remoteExec.run` 在 `ctx.Done()` 时向会话发送 `SIGKILL`；
  - 解包/上传等不可中断点会等到当前操作返回或会话关闭；
- 取消后可能留下 `/tmp/packrun-*`、`.incoming-*` 或部分目标文件，需要人工清理。

### 9.3 服务重启恢复

启动时 `RecoverInterruptedTasks`：

- 所有 `pending/uploading/verifying/executing` 任务 → `failed`，
  `message=服务重启，任务执行中断`；
- 对应 `running` 步骤 → `failed`；
- 写 `task.recover` 审计（`actor=system`）。

没有自动续跑机制；需要重新发起任务。

## 10. 运维注意事项

| 事项 | 说明 |
|---|---|
| 磁盘空间 | SSH 备份使用 `cp -a`，会占用双份空间；`keepReleases` 控制保留数量 |
| 备份清理 | 只清理 `<target>.bak-*`；其他文件不动 |
| 包仓库 | 没有删除接口，容量受 `storage.max_total_mb` 限制 |
| 脚本版本 | 任务记录脚本名与版本；执行时读取最新内容并写入步骤日志 |
| 目录变更 | 任务创建时快照路径；排队期间目录被改动或删除会直接失败 |
| 脚本删除 | 排队期间脚本被删除会直接失败，不会静默跳过 |
| 并发调优 | 全局 `max_concurrent` 与服务器 `max_concurrent` 共同生效；同目录强制串行 |
| 大包上传 | 中控与 Nginx 均限制 200MB；Nginx 需 `client_max_body_size 200m` 且关闭请求缓冲 |
| 执行日志 | 步骤输出无自动截断，大脚本/长输出会增大 SQLite 体积 |
