# Packrun 路线图

> 本文档规划后续演进方向，优先级依据当前能力盘点与
> [部署与使用手册](03-部署与使用手册.md)「已知限制」（§21）整理。
> 路线图不构成发布承诺：条目按里程碑滚动推进，完成后标注版本并同步
> §21 与 [wiki 10-测试与已知限制](wiki/10-测试与已知限制.md)，避免文档漂移。

## 规划原则

1. **先还可靠性欠账，再堆新能力。** 中控类工具的信任基础是「结果可预期」：
   任务不因重启凭空消失、排队内容不被偷换、告警不重复轰炸。
2. **每项带验收标准。** 完成的判定以验收标准逐条核对为准，不以「代码写完」为准。
3. **保持轻量默认形态。** 单二进制 + SQLite + SSH 拉模式是默认；Agent、PostgreSQL
   等重能力一律做成可选模式，不抬高最小部署门槛。

## 里程碑总览

| 里程碑 | 主题 | 内容 | 状态 |
|---|---|---|---|
| M1 | 可靠性收口 | 任务续跑、脚本快照、告警去重落库、发布 manifest 干净替换、上传记录幂等 | 规划中 |
| M2 | 执行引擎与发布能力 | 目标机 Agent、分批灰度、蓝绿发布、通知渠道扩展、可观测页 | 规划中 |
| M3 | 平台化 | OpenAPI + Token + 事件回调、审批流、存储可替换、制品源扩展 | 远期 |

## M1 可靠性收口

### M1-1 任务持久化与重启续跑

**背景**：§21.6 —— 所有未完成任务重启后直接标记失败，不续跑。重启中控机等于放弃
所有在途发布，是「敢不敢在生产用」的第一道心理门槛。

**方案要点**：

- 任务执行计划（目标目录、安装包、脚本引用）与步骤进度落库，重启时不再一律判失败，
  而是进入「待恢复」状态，由人工选择续跑或标记失败。
- 续跑以步骤状态为准：已完成步骤不重复执行（解包、校验类步骤需幂等）。
- 保留现有 `task.recover` 审计，区分「自动判失败」（兼容旧行为的可配置开关）与「人工续跑」。

**验收标准**：

- [ ] `kill -9` 中控进程后重启，运行中任务进入「待恢复」而非直接失败；
- [ ] 选择续跑后，已完成步骤不重复执行，剩余步骤按原计划继续；
- [ ] 任务详情页能看到每一步的持久化状态；
- [ ] 审计日志区分续跑与标记失败两种人工动作。

### M1-2 脚本内容快照

**背景**：§21.7 —— 排队任务执行时按脚本 ID 重读记录，排队期间编辑脚本会偷换内容。

**方案要点**：创建任务时将脚本内容（或版本 + 哈希）快照进任务记录，执行引擎只读快照；
脚本列表对「被未完成任务引用」给出提示，编辑前可感知影响面。

**验收标准**：

- [ ] 排队期间编辑脚本，已排队任务仍执行创建时的内容；
- [ ] 任务详情页可查看当时执行的脚本原文；
- [ ] 脚本编辑入口对被未完成任务引用的脚本显示警告。

### M1-3 告警去重落库

**背景**：§21.13 —— 去重窗口在进程内存（`internal/notify` 的 `Webhook.allow`），
重启后同一失败任务或证书会重复告警一次。

**方案要点**：去重键与上次发送时间持久化（库表或 KV），发送前查库判定；
窗口时长配置化。

**验收标准**：

- [ ] 重启后窗口期内同一事件不重复发送；
- [ ] 窗口时长可通过配置调整；
- [ ] 既有 `notify_test.go` 全部通过，新增持久化去重的回归测试。

### M1-4 发布 manifest 与干净替换

**背景**：§21.1 —— zip 部署不受「仅新增/禁止覆盖」约束、不删除多余旧文件；
§21.3 —— 自动恢复只覆盖目标目录，无法感知本次发布动了哪些文件。

**方案要点**：

- 解包时生成发布 manifest（相对路径 + SHA256），随任务落库；
- 目录策略新增「干净替换」：按 manifest 删除本次未包含的旧文件，仅限部署目录内，
  执行前展示差异清单供确认；
- 回滚与失败恢复基于 manifest 感知影响范围（不扩展到脚本副作用，见 §21.3 保留说明）。

**验收标准**：

- [ ] 干净替换后目录内旧文件与 manifest 一致，目录外内容不受影响；
- [ ] 差异清单（将删除/将覆盖/仅新增）在任务详情页可查；
- [ ] 「仅新增/禁止覆盖」策略对 zip 同样生效；
- [ ] 失败自动恢复行为与 manifest 一致。

### M1-5 上传登记幂等

**背景**：§21.4 —— 上传响应丢失时前端自动重试，服务端留下重复包记录。

**方案要点**：上传登记引入幂等键（SHA256 + 上传会话 token），同键重复登记覆盖而非新增。

**验收标准**：

- [ ] 弱网重试后「最近上传」不再出现重复条目；
- [ ] 既有 3 天未引用记录清理逻辑保持不变。

## M2 执行引擎与发布能力

### M2-1 目标机 Agent（可选模式）

**背景**：纯 SSH 拉模式下 `healthz` 探测不到目标机（§21.5），目标机指标只有
人工点「检测」时的一次性快照。

**方案要点**：

- 轻量 Go agent：出站长连（或轮询）中控，接收指令、回传执行结果，心跳上报
  负载/内存/磁盘；SSH 模式保留为默认，agent 按服务器逐台启用；
- 心跳数据落库形成资源趋势，agent 离线触发告警；
- `healthz` 可选纳入 agent 在线状态（配置开关，避免单点 agent 故障拖垮整个健康检查）。

**验收标准**：

- [ ] agent 模式下部署/检测走 agent 通道，结果语义与 SSH 模式一致；
- [ ] 服务器页可查看资源趋势（至少 7 天）；
- [ ] agent 离线超阈值产生告警（走通知渠道）；
- [ ] agent 单二进制 ≤ 10MB，提供 systemd 托管文档；
- [ ] 不启用 agent 的环境行为与现状完全一致。

### M2-2 项目分批发布（灰度）

**背景**：项目批量发布目前全量一把推，一次坏包会同时打到全部绑定目录。

**方案要点**：发布批次拆为 N 批（按台数或百分比），批间推进支持
「自动（健康检查通过）/手动确认」两种模式；任一批失败默认暂停后续批次。

**验收标准**：

- [ ] 指定多台分 2 批发布，第二批等待确认后再执行；
- [ ] 首批失败时第二批不执行，批次整体进入「已暂停」状态，可人工继续或终止；
- [ ] 批次划分、确认人与推进时间入审计。

### M2-3 蓝绿 / 符号链接发布策略

**方案要点**：目录策略新增 symlink 发布模式——包解到 `releases/<时间戳>/`，
前置校验通过后原子切换 `current` 软链；保留版本数复用现有
`package_keep_releases` 窗口；回滚 = 切回旧 release，不重传包。

**验收标准**：

- [ ] 切换原子完成，无中间不可用窗口；
- [ ] 回滚秒级完成且不消耗包上传；
- [ ] 旧 release 按 `package_keep_releases` 窗口回收，与包仓库 GC 协同不误删。

### M2-4 通知渠道扩展

**背景**：`internal/notify` 已有 Webhook 发送器，支持企微格式与通用格式，
去重窗口为进程内实现（随 M1-3 落库）。

**方案要点**：发送器接口化，补钉钉、飞书、SMTP 邮件三种渠道；支持多渠道并行
与按事件类型路由（如仅 prod 失败发邮件）；渠道配置页面化（仅管理员）。

**验收标准**：

- [ ] 同一事件可同时推送到多个渠道，各渠道消息格式正确；
- [ ] 按事件类型路由生效（可配置某渠道只收特定事件）；
- [ ] 渠道增删改在页面上完成且入审计；
- [ ] 未配置任何渠道时行为为 Noop，不报错。

### M2-5 可观测页

**方案要点**：任务成功率/耗时趋势（按天聚合）、目标机资源趋势（依赖 M2-1 心跳或
检测历史落库）、包仓库容量趋势；图表复用现有 `MetricRing` 组件风格；
对外提供只读统计 API（`/api/v1/stats/*`，需认证），供大屏等场景消费。

**验收标准**：

- [ ] 概览页可查看近 30 天任务趋势与包仓库容量；
- [ ] 统计 API 只读、需认证、不暴露任务明细与服务器凭据相关字段；
- [ ] 无历史数据时页面展示空态而非报错。

## M3 平台化（远期）

### M3-1 OpenAPI + API Token + 事件回调

**方案要点**：独立于用户 JWT 的 API Token（作用域：`deploy:trigger`、`read` 等），
创建/吊销页面化并入审计；CI 触发发布、任务完成后回调 Webhook（带任务 ID 与结果
摘要，失败重试有上限）。

**验收标准**：

- [ ] Token 可创建、吊销、查最后使用时间，全部入审计；
- [ ] CI 用 Token 走完「上传 → 触发发布 → 查询结果」全链路；
- [ ] 事件回调失败重试有上限且可查投递记录；
- [ ] prod 环境经 API 触发仍受 step-up / 审批（M3-2）约束。

### M3-2 发布审批流

**背景**：prod 发布目前仅 TOTP step-up，适合单人操作，不适合团队协作场景。

**方案要点**：环境级开关「需审批」——发起人提交后任务进入待审批，审批人批准后入队；
审批人角色独立于项目成员；支持撤回与超时自动过期。

**验收标准**：

- [ ] 未批准任务不执行，可被发起人撤回；
- [ ] 批准/驳回/超时均入审计并走通知渠道；
- [ ] API Token 发起的发布同样经过审批。

### M3-3 存储可替换 PostgreSQL（可选）

**方案要点**：`internal/store` 集中持久化已具备抽象基础，新增 PostgreSQL 实现；
SQLite 保持默认，仅多中控实例 / HA 场景启用；提供一次性迁移工具（导出导入）。

**验收标准**：

- [ ] 同一套 API 与测试在两种存储下通过；
- [ ] 文档给出 SQLite → PostgreSQL 迁移步骤与回退方式；
- [ ] 默认部署仍为零依赖 SQLite。

### M3-4 制品源扩展

**方案要点**：对接 Git 平台拉取构建产物（Release 附件 / 产物 URL）作为安装包来源；
支持 Docker 镜像 tar 作为包类型；包仓库可视化「包 ↔ 项目 / 目录 / 任务」引用关系。

**验收标准**：

- [ ] 从制品 URL 拉取并完成 SHA256 校验、登记、发布全链路；
- [ ] 包详情页可查全部引用关系，被引用的包不受 GC 影响（与现有版本窗口 GC 协同）。
