# 第一部分 部署指南

## 1. 系统架构与部署拓扑

```
外网浏览器
  │ HTTPS 443
  ▼
[可选] Nginx / 负载均衡（TLS 终止、反代、限流、上传体积、真实 IP）
  │
  ▼
[可选] frp（frps 公网 → frpc 中控机）← 仅公网穿透场景
  │
  ▼
Go 中控服务 packrund（Gin + SQLite + 包仓库 + 内嵌前端，默认监听 0.0.0.0:9000）
  │ SSH（凭据按引用解析，不落明文）
  ▼
业务服务器（部署目录 + 远程脚本）
```

按中控服务所在网络位置，有三种推荐拓扑：

| 拓扑 | 适用 | 组件分布 |
|---|---|---|
| **A. 单包直连** | 内网访问，或前面已有 HTTPS 负载均衡 | 中控机：packrund（内嵌前端）。无需 Nginx / frp |
| **B. 单包 + Nginx** | 需要域名与 HTTPS 终止 | 中控机：packrund + Nginx（只做 TLS 反代）。无需 frp |
| **C. 公网穿透** | 中控机没有公网入口 | 跳板机：Nginx + frps；中控机：packrund + frpc |

前端构建产物通过 `go:embed` 打进 `packrund`，页面与 `/api` 天然同源（前端 API 基地址
是 `/api/v1` 相对路径，见 `web/src/api/http.ts:4`），不再需要单独部署前端静态文件；
`make build` 会完成前端构建与嵌入。Go 服务自身不提供 TLS，需要 HTTPS 时仍由 Nginx
或负载均衡终止。未内嵌前端的单独后端构建，路由仍只有 `/api/v1` 与 `/healthz`
（见 `server/internal/api/router.go`）。

安全底线：**直连时用防火墙/安全组限制来源；不需要公网访问时把 `server.addr` 改为
`127.0.0.1:9000`，公网入口只暴露 TLS 443**。

> 单包直连（拓扑 A）默认监听 `0.0.0.0:9000`，请务必限制来源 IP；
> 改为 `127.0.0.1:9000` 后需同机 Nginx / frp 才能从外部访问。

## 2. 环境要求

| 组件 | 要求 | 说明 |
|---|---|---|
| Go（构建机） | ≥ 1.26.0 | `server/go.mod` 声明 `go 1.26.0` |
| Node.js（构建机） | 18 / 20 / ≥22 | Vite 6 的 engines 要求 |
| pnpm | 兼容 lockfile 9.0 | 建议用 pnpm 9/10 |
| 中控机 OS | Linux（glibc） | 单二进制，无运行时依赖；需可写 `data/` 目录 |
| 目标业务服务器 | SSH 可达 + 常用命令 | 无需安装任何 agent，依赖见 §15.4 |
| 浏览器 | 现代桌面浏览器 | Chrome / Edge / Firefox 近两年版本 |

## 3. 构建

### 3.1 后端

仅需单独构建后端时使用。生产推荐 §3.3 单包构建。

```bash
cd server
go build -trimpath -o bin/packrund ./cmd/packrund
```

产出单个二进制 `bin/packrund`。交叉编译示例（中控机为 linux/amd64、构建机为 mac）：

```bash
cd server
CGO_ENABLED=0 GOOS=linux GOARCH=amd64 go build -trimpath -o bin/packrund-linux-amd64 ./cmd/packrund
```

> SQLite 使用纯 Go 驱动（glebarez/sqlite），交叉编译无需 CGO。

### 3.2 前端

```bash
cd web
pnpm install --frozen-lockfile
pnpm type-check     # vue-tsc 类型检查；build 不会自动执行
pnpm build          # 产物输出到 web/dist/
```

把 `web/dist/` 整个目录同步到 Nginx 所在主机的站点根（如 `/var/www/packrun`）；
使用 §3.3 单包构建时无需这一步。注意：

- Vite 未配置 `base`，**只能部署在域名根路径**（`https://deploy.example.com/`），
  不支持 `/packrun/` 这类子路径。
- 前端使用 History 路由；单包模式由 packrund 提供 SPA 回退，独立静态部署需在 Nginx
  配置回退（见 §7）。

### 3.3 单包构建（推荐）

在仓库根目录执行：

```bash
make build
# 前端构建 → 同步到 server/internal/webui/dist → go build
# 产物：server/bin/packrund（前端已内嵌，单文件分发）
GOOS=linux GOARCH=amd64 make build   # 交叉编译
```

`make build` 优先使用仓库内置的 `.tools/go`，否则使用 PATH 中的 `go`。它等价于
§3.2 的 `pnpm build` + 产物同步 + §3.1 的 `go build`；之后只需分发 `packrund`
一个文件，页面与 API 均由该进程提供。

生成可直接上传服务器的部署包（默认 `linux/amd64`）：

```bash
make package
# 产物：dist/packrun-linux-amd64.tar.gz
PKG_GOARCH=arm64 make package   # ARM 服务器
```

包内目录：

```
packrun-linux-amd64/
├── start.sh
├── deploy/                nginx / frp 样例
└── server/
    ├── bin/packrund
    └── configs/config.yaml
```

## 4. 配置说明

配置文件 `-config`（默认 `configs/config.yaml`），加载优先级：
**内置默认值 < YAML < 环境变量**。相对路径（`./data/...`）按进程**当前工作目录**解析，
与二进制位置无关——systemd 部署时务必固定 `WorkingDirectory`，或将路径改为绝对值。

### 4.1 完整配置项

| 配置项 | 默认值 | 环境变量覆盖 | 说明 |
|---|---|---|---|
| `server.addr` | `0.0.0.0:9000` | `PACKRUN_ADDR` | HTTP 监听地址；直连时限制来源，前置代理时可改回 `127.0.0.1:9000` |
| `server.mode` | `debug` | — | `debug` / `release` / `test`，生产必须 `release` |
| `server.base_path` | `/packrun` | `PACKRUN_BASE_PATH` | 对外部署子路径，默认 `/packrun`；改根路径填 `/`，需与 Nginx `location` 一致，见 §7.3 |
| `server.allowed_origins` | `["http://localhost:5173"]` | — | CORS 白名单；release 下禁止 `*`。同源部署时浏览器不触发 CORS，保持默认即可 |
| `server.trusted_proxies` | `["127.0.0.1/32","::1/128"]` | — | 信任哪些代理写入的 `X-Forwarded-For`，见 §7.2 |
| `auth.jwt_secret` | dev 占位值 | `PACKRUN_JWT_SECRET` | JWT HS256 密钥，≥32 字节且不得用默认值 |
| `auth.token_ttl_minutes` | `480` | — | 登录令牌有效期（分钟），默认 8 小时 |
| `auth.otp_issuer` / `otp_period` / `otp_skew` | `Packrun` / `30` / `1` | — | TOTP 参数，一般不改 |
| `storage.db_path` | `./data/packrun.db` | — | SQLite 主库（WAL 模式） |
| `storage.package_dir` | `./data/packages` | — | 上传包仓库，按 `YYYYMM/` 归档 |
| `storage.sandbox_root` | `./data/sandbox` | — | local 模式沙箱根目录（ssh 模式也会创建） |
| `storage.max_total_mb` | `20480` | — | 包仓库总容量上限（MB），`0` 不限制；**只统计包目录**，磁盘规划还需加上数据库、沙箱与部署备份 |
| `storage.task_log_retention_days` | `90` | — | 任务步骤日志正文保留天数，超期只清正文、保留步骤时间线；`0` 表示不清理 |
| `storage.task_retention_days` | `180` | — | 终态任务（成功/失败/取消）保留天数，超期连同步骤一起删除；`0` 表示不清理 |
| `storage.audit_retention_days` | `180` | — | 审计日志保留天数；`0` 表示不清理。合规要求更久时先导出再调大 |
| `storage.package_keep_releases` | `10` | — | 每个部署目录保留最近多少个版本的安装包，保证最近 N 次回滚可用；`0` 关闭版本回收 |
| `storage.package_keep_days` | `7` | — | 最近多少天内上传的安装包一律保留；`0` 表示只按版本窗口判断 |
| `alert.webhook_url` | 空 | `PACKRUN_ALERT_WEBHOOK` | 告警推送地址；留空只写服务日志（`[alert]` 前缀） |
| `alert.format` | `wecom` | — | `wecom` 企业微信群机器人 / `generic` 通用 JSON |
| `alert.min_interval_seconds` | `600` | — | 同类告警去重窗口（秒），避免故障期间刷屏 |
| `alert.check_interval_seconds` | `60` | — | 后台巡检间隔（秒），`0` 关闭巡检 |
| `alert.disk_min_free_mb` | `1024` | — | 包目录磁盘剩余低于该值（MB）告警，`0` 不检查 |
| `alert.cert_files` | `[]` | — | 需要监控到期的证书文件（PEM 全链） |
| `alert.cert_expire_days` | `14` | — | 证书剩余天数低于该值告警，`0` 不检查 |
| `deploy.mode` | `ssh` | `PACKRUN_DEPLOY_MODE` | `local` 沙箱（开发/演示，包落 `data/sandbox/`）/ `ssh` 生产 |
| `deploy.max_concurrent` | `3` | `PACKRUN_MAX_CONCURRENT` | 全局任务并发；非正整数会被忽略并回落 3 |
| `deploy.step_delay_ms` | `350` | — | 步骤间人为延迟，local 与 ssh 都生效；生产可设 `0` |
| `deploy.max_pending_per_user` | `10` | — | 单用户未终态任务上限 |
| `bootstrap.admin_username` | `admin` | — | 首次初始化管理员用户名 |
| `bootstrap.admin_password` | `Admin@12345` | `PACKRUN_ADMIN_PASSWORD` | **仅空库首次初始化时生效**，不是密码重置手段 |

另有独立环境变量：

| 环境变量 | 说明 |
|---|---|
| `PACKRUN_SSH_INSECURE=1` | SSH 跳过主机指纹校验；**仅 debug 模式允许**，release 下设置会拒绝启动 |
| `env:<VAR>`（凭据引用） | 服务器凭据可引用任意环境变量，如 `env:PROD_SSH_PASSWORD`；变量需注入 packrund 进程 |

### 4.2 内置的硬限制（不可配置）

| 项目 | 值 |
|---|---|
| 单安装包体积 | 200 MB，仅 `.zip` / `.jar`，并校验文件头 |
| ZIP 条目数 / 解包体积预算 | 20000 条 / 未配置目录阈值时 1 GB |
| 非 multipart 请求体 | 1 MB |
| HTTP 超时 | ReadHeader 10s / Read 10min / Write 15min / Idle 120s |
| SSH 建连 / 单条远程命令 | 10s / 15min |
| 脚本超时 | 默认 120s，可配 1–3600s |
| 登录失败锁定 | 同账号 5 次或同 IP 30 次 → 锁 5 分钟 |
| 单步任务日志 | 头部 8KB + 尾部 24KB，超出部分丢弃并标注省略字节；单行截断到 4KB |

> 上传接口单独放宽了读写超时（Read 10min / Write 15min），200MB 包在弱网或经 frp 隧道
> 上传时有足够余量；Nginx 侧 `client_body_timeout` 与 `proxy_*_timeout` 都放宽到 600s。
> 前端 axios 上传超时为 15min，与后端一致。

### 4.3 上传链路的可靠性保证

上传是整条链路里最容易受网络与磁盘影响的环节，当前实现做了以下约束：

| 机制 | 行为 |
|---|---|
| 流式写入 | 直接用 multipart 流写进包仓库，不再经 `ParseMultipartForm` 先落系统临时目录再复制，省一半磁盘 IO 与空间 |
| 原子提交 | 先写 `<目标>.incoming-<随机>`，`fsync` 后 `rename` 到最终路径；崩溃/断连/磁盘满都不会留下半截包 |
| 残留回收 | 每小时维护时清理超过 1 小时的 `.incoming-*` 临时文件，避免异常退出占空间 |
| 提前拒绝 | `Content-Length` 已超 200MB 时在读包之前返回 413；写入过程按实际字节再判一次 |
| 断连提示 | 客户端中断返回「上传已中断，请检查网络后重试」，磁盘满返回 507「服务器磁盘空间不足」 |
| 前端重试 | 网络中断 / 超时 / 429 / 502 / 503 / 504 自动重试一次，界面提示「正在第 N 次自动重试」 |

> 只有响应丢失的极端情况会留下一条重复包记录（服务端已登记但前端没收到响应），
> 在「最近上传」里删除即可；未被任务引用的上传记录 3 天后会自动清理。

### 4.4 健康检查与告警

`GET /healthz` 是**深检查**，不再只证明进程活着：

```json
{
  "status": "ok",
  "version": "v0.2.0",
  "uptimeSec": 3600,
  "time": "2026-11-18T19:50:00+08:00",
  "checks": {
    "database":   { "status": "ok", "latencyMs": 1 },
    "packageDir": { "status": "ok", "detail": "已用 512 MB / 上限 20480 MB（2%）" },
    "disk":       { "status": "ok", "detail": "剩余 69142 MB / 共 233752 MB" },
    "tasks":      { "status": "warn", "detail": "最近 1 小时 2 个任务失败" }
  }
}
```

- `database`：连接可用 + `PRAGMA quick_check` 通过 + 库文件目录可写；任一不满足记为 `fail`。
- `packageDir`：目录可写，并汇报配额占用；超过 90% 记为 `warn`。
- `disk`：包目录所在磁盘剩余低于 `alert.disk_min_free_mb` 记为 `fail`。
- `tasks`：最近 1 小时失败任务数，只作提示，不影响可用性。
- **任一 `fail` → HTTP 503 + `status: degraded`**，可直接给负载均衡做健康判定。
- `checks.*.metrics` 是给页面渲染用的结构化数字（MB 与百分比），`detail` 是给人读的文案。
- 结果缓存 5 秒：负载均衡与概览页几秒一次轮询时不会反复执行 `PRAGMA quick_check`。

**「概览」页直接展示这份报告**：四张卡片（中控机状态、包仓库占用、磁盘剩余、纳管服务器）
加一张健康检查明细表，30 秒自动刷新；有硬性检查失败时页面顶部给出错误提示。
任务统计与最近任务不再占用概览页，统一放到「任务」页。

探针不鉴权，因此**不返回运行模式、部署方式、目录绝对路径**等拓扑信息，只给可用性结论。

后台每 `alert.check_interval_seconds` 秒巡检一次，命中以下情况推送告警：

| 场景 | 级别 | 去重键 |
|---|---|---|
| 磁盘剩余低于阈值 | error | `disk:free` |
| 包仓库占用 ≥90% | warn | `disk:quota` |
| 新出现的失败任务（每个任务一次） | error | `task:<id>` |
| 证书剩余天数低于阈值 | error | `cert:<path>` |
| 证书文件读取失败 | warn | `cert:read:<path>` |

推送示例（企业微信群机器人）：把群机器人 Webhook 地址填到 `alert.webhook_url`，
`format: wecom` 即可；自建告警平台用 `format: generic`，收到的是
`{"source":"packrun","level":"error","title":"...","text":"..."}`。
未配置地址时只写服务日志：

```
[alert] error：部署任务失败 任务 20261118-001｜app.zip → /opt/apps/order｜操作人 alice
```

## 5. 生产启动约束

`server.mode: release`（或 `test`）时，以下任一不满足都会**拒绝启动**：

1. `PACKRUN_JWT_SECRET`（或 YAML 中的 `auth.jwt_secret`）非空、非 dev 默认值、长度 ≥32 字节；
2. `PACKRUN_ADMIN_PASSWORD`（或 YAML 中 `bootstrap.admin_password`）非空且不等于 `Admin@12345`；
3. `server.allowed_origins` 不含 `*`；
4. `deploy.mode: ssh` 时未设置 `PACKRUN_SSH_INSECURE=1`。

推荐把秘密放环境变量而非 YAML，避免落盘。生成方式：

```bash
openssl rand -hex 32   # JWT 密钥
openssl rand -hex 16   # frp token 同样用它生成
```

> `release` **不会**强制 `deploy.mode=ssh`，也不会强制监听回环——这两项仍需在配置里正确设置。

### 5.1 首次初始化行为

- 用户表为空时创建管理员（`bootstrap.*`）；`debug` 模式下额外创建演示账号
  `auditor / Audit@12345` 与三台演示服务器、目录、脚本。**release 模式不创建任何演示数据**。
- 用户表非空时，`PACKRUN_ADMIN_PASSWORD` 不会再生效（不重置已有管理员密码）。
- 已有 debug 环境切到 release 时，已存在的 `auditor` 账号与演示数据**不会自动清理**，
  需在用户管理中删除或禁用该账号（`auditor` 若仍关联项目/任务，需先处理关联）。
- 每次重启会把 `pending/uploading/verifying/executing` 的任务统一标记为失败并写
  `task.recover` 审计记录，任务**不会自动续跑**。

## 6. systemd 托管

单包部署时只需要托管 packrund 一个 systemd 服务：前端已内嵌在二进制中，不需要再
同步 `web/dist` 或单独运行静态文件服务；Nginx 仅在需要域名 / HTTPS 时保留（见 §7）。
也可以把 `ExecStart` 指向仓库根目录的 `start.sh`（保持 `server/` 目录布局），由脚本
统一配置监听地址、子路径与环境变量。注意：`start.sh` 不带参数时是**后台启动**
（nohup 守护），交给 systemd 托管必须显式使用 `./start.sh --foreground`。

假定安装根为 `/opt/packrun`，运行账号 `packrun`：

```bash
# 目录准备
mkdir -p /opt/packrun/server/{bin,configs}
install -m 0755 bin/packrund /opt/packrun/server/bin/packrund
install -m 0600 configs/config.yaml /opt/packrun/server/configs/config.yaml
useradd -r -s /usr/sbin/nologin packrun
chown -R packrun:packrun /opt/packrun
```

密钥放独立 env 文件（权限 600）：

```bash
# /etc/packrun.env
PACKRUN_JWT_SECRET=<openssl rand -hex 32 的输出>
PACKRUN_ADMIN_PASSWORD=<首次初始化口令>
PACKRUN_DEPLOY_MODE=ssh
# 服务器凭据引用所需的环境变量也在此注入，例如：
# PROD_SSH_PASSWORD=xxx
```

```ini
# /etc/systemd/system/packrund.service
[Unit]
Description=Packrun 中控服务
After=network-online.target
Wants=network-online.target

[Service]
Type=simple
User=packrun
Group=packrun
# 关键：数据路径是相对路径，必须固定工作目录到 server/
WorkingDirectory=/opt/packrun/server
ExecStart=/opt/packrun/server/bin/packrund -config /opt/packrun/server/configs/config.yaml
EnvironmentFile=/etc/packrun.env
Restart=on-failure
RestartSec=3
NoNewPrivileges=true
ProtectSystem=strict
ReadWritePaths=/opt/packrun/server/data
PrivateTmp=true

[Install]
WantedBy=multi-user.target
```

```bash
systemctl daemon-reload
systemctl enable --now packrund
journalctl -u packrund -f          # 服务日志输出到 stdout，由 journald 收集
```

## 7. Nginx 入口配置

**单包模式（拓扑 A / B）可跳过本节**：packrund 已内嵌前端并自带 SPA 回退，默认部署在
`/packrun` 子路径，直接访问 `http://<中控机>:9000/packrun/` 即可。需要域名与 HTTPS 时，
Nginx 只做 TLS 终止和全站反代，把下面示例中的 `root` / `try_files` 换成：

```nginx
location / {
    proxy_pass http://127.0.0.1:9000;
    proxy_http_version 1.1;
    proxy_set_header Host              $host;
    proxy_set_header X-Real-IP         $remote_addr;
    proxy_set_header X-Forwarded-For   $proxy_add_x_forwarded_for;
    proxy_set_header X-Forwarded-Proto $scheme;
    proxy_request_buffering off;
    proxy_send_timeout 600s;
    proxy_read_timeout 600s;
}
```

`deploy/nginx.conf.example` 只演示了纯反代写法（`location /` 全部转发到 18080），
它不托管前端静态文件。下面的完整示例是「Nginx 托管前端静态文件 + frp」模式，
适用于未内嵌前端的单独构建；拓扑 B（跳板机 + frp）直接把 `18080` 换成 `9000` 即可：

```nginx
# /etc/nginx/conf.d/packrun.conf（http 上下文限流区）
limit_req_zone $binary_remote_addr zone=packrun:10m rate=10r/s;
limit_req_zone $binary_remote_addr zone=packrun_login:10m rate=5r/m;

server {
    listen 80;
    server_name deploy.example.com;
    return 301 https://$host$request_uri;
}

server {
    listen 443 ssl;
    http2 on;
    server_name deploy.example.com;
    server_tokens off;

    ssl_certificate     /etc/nginx/certs/deploy.example.com.pem;
    ssl_certificate_key /etc/nginx/certs/deploy.example.com.key;
    ssl_protocols TLSv1.2 TLSv1.3;
    ssl_prefer_server_ciphers off;
    ssl_session_cache shared:SSL:10m;
    ssl_session_timeout 1d;

    add_header Strict-Transport-Security "max-age=31536000; includeSubDomains" always;
    add_header X-Content-Type-Options "nosniff" always;
    add_header X-Frame-Options "DENY" always;
    add_header Referrer-Policy "no-referrer" always;
    add_header Permissions-Policy "geolocation=(), microphone=(), camera=()" always;
    add_header Content-Security-Policy "default-src 'self'; script-src 'self'; style-src 'self' 'unsafe-inline'; img-src 'self' data:; font-src 'self' data:; connect-src 'self'; frame-ancestors 'none'; base-uri 'self'; form-action 'self'" always;

    # 单包上限 200MB 由服务端判定；这里留 10MB 余量吸收 multipart 边界与字段头开销，
    # 否则接近 200MB 的包会被 Nginx 先拒成 413 HTML 页，前端拿不到可读错误
    client_max_body_size 210m;
    client_body_timeout  600s;

    limit_req zone=packrun burst=20 nodelay;

    # 前端静态文件（web/dist 同步到该目录）
    root /var/www/packrun;
    index index.html;

    # API 反代：拓扑 A 指向 127.0.0.1:9000；拓扑 B 指向 frps 的 127.0.0.1:18080
    location /api/ {
        limit_req zone=packrun burst=20 nodelay;
        proxy_pass http://127.0.0.1:18080;
        proxy_http_version 1.1;
        proxy_set_header Host              $host;
        proxy_set_header X-Real-IP         $remote_addr;
        proxy_set_header X-Forwarded-For   $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
        proxy_request_buffering off;      # 大包上传不缓冲
        proxy_buffering         off;
        proxy_connect_timeout   10s;
        proxy_send_timeout      600s;
        proxy_read_timeout      600s;
    }

    # 登录接口独立限流（5 次/分钟），与服务端失败锁定配合
    location = /api/v1/auth/login {
        limit_req zone=packrun_login burst=5 nodelay;
        proxy_pass http://127.0.0.1:18080;
        proxy_http_version 1.1;
        proxy_set_header Host              $host;
        proxy_set_header X-Real-IP         $remote_addr;
        proxy_set_header X-Forwarded-For   $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
        proxy_connect_timeout   10s;
        proxy_send_timeout      60s;
        proxy_read_timeout      60s;
    }

    location = /healthz {
        proxy_pass http://127.0.0.1:18080/healthz;
        access_log off;
    }

    # SPA 回退：/projects、/tasks/1 等前端路由全部落到 index.html
    location / {
        try_files $uri $uri/ /index.html;
    }
}
```

### 7.1 要点

- `/api/`、`/api/v1/auth/login`、`/healthz` 三个 location 必须在 `location /`（SPA 回退）之前生效，
  避免前端路由吞掉 API。
- 只有「Nginx 托管前端静态文件」模式才需要 `root` + `try_files`；单包模式直接
  把 `location /` 反代到 packrund 即可。

### 7.2 真实 IP 与 trusted_proxies

- Go 收到的直接 TCP 对端是 frpc（回环）或本机 Nginx（回环），XFF 由最外层 Nginx 写入并经隧道透传。
  因此**仅当** packrund 的 9000 只监听回环、frps 的 18080 也只绑定回环时，才保留默认
  `trusted_proxies: [127.0.0.1/32, ::1/128]`，此时登录锁定与审计能记录真实客户端 IP。
- 若 18080 / 9000 有任何非回环可达的可能，**清空** `trusted_proxies`（`[]`），
  否则客户端可伪造 `X-Forwarded-For` 绕过登录锁定、污染审计 IP。
- 登录锁定有两个维度：同账号 5 次失败、同 IP 30 次失败，均锁 5 分钟。

### 7.3 子路径部署（默认 /packrun）

默认部署在 `https://deploy.example.com/packrun/` 子路径；`./start.sh --print-nginx`
默认就会输出与之匹配的 `location` 配置。如需改回域名根路径：

1. 启动时显式指定根路径：
   ```bash
   PACKRUN_BASE_PATH=/ ./start.sh
   ```
   应用会把 `<base href="/">` 注入页面，前端资源、Vue 路由与 `/api/v1` 请求都不带前缀；
   无需重新构建前端。
2. 生成对应的 Nginx 配置：
   ```bash
   PACKRUN_BASE_PATH=/ ./start.sh --print-nginx
   ```
   把输出的 `location` 块加入站点的 `server {}`。
3. **关键**：`proxy_pass` 后不要带 URI（不要写成 `http://127.0.0.1:9000/`）。
   带尾斜杠会剥离前缀，与应用内的子路径配置不一致，导致跳转循环或 404。
4. 访问 `https://deploy.example.com/` 验收；如使用默认子路径，则访问
   `https://deploy.example.com/packrun/`，静态资源为 `/packrun/assets/...`，
   接口为 `/packrun/api/v1/...`。健康检查始终使用根路径 `/healthz`。

> 使用 `start.sh` 时，显式设置 `PACKRUN_BASE_PATH`（环境变量或脚本内修改）会覆盖
> `config.yaml` 的 `server.base_path`；未设置时沿用配置文件（默认 `/packrun`）。
> 无论哪种方式，都必须与 Nginx 的 `location` 完全一致。

## 8. frp 隧道（公网穿透）

拓扑 C 需要 frp；拓扑 A / B 跳过本节。样例见 `deploy/frps.toml`、`deploy/frpc.toml`。

**跳板机 frps**：

```toml
bindPort = 7000
proxyBindAddr = "127.0.0.1"          # 18080 只监听回环，仅本机 Nginx 可访问
auth.method = "token"
auth.token = "<openssl rand -hex 32，与 frpc 一致>"
allowPorts = [{ start = 18080, end = 18089 }]
transport.tcpMux = true
```

**中控机 frpc**：

```toml
serverAddr = "frp.example.com"
serverPort = 7000
auth.method = "token"
auth.token = "<同 frps>"
[[proxies]]
name = "packrun-web"
type = "tcp"
localIP = "127.0.0.1"
localPort = 9000                      # packrund 监听地址
remotePort = 18080                    # frps 侧回环端口，供 Nginx 反代
```

防火墙要求：跳板机只对公网开放 80/443 与 frp 的 7000（建议 7000 另加来源白名单）；
18080 绝不对公网开放。业务服务器的 SSH 端口只需**中控机**可达，无需公网暴露。

## 10. 备份与恢复

**数据库与包仓库是同一个逻辑备份单元**——数据库只存包的相对路径
（`StorageKey`），只备份数据库会留下大量悬空包记录，历史发布与项目回滚都会失败。

### 10.1 离线备份（推荐）

```bash
# 1. 确认无运行中任务后停止服务
systemctl stop packrund

# 2. 一并打包数据目录与配置
tar -C /opt/packrun/server -czf /backup/packrun-$(date +%F).tar.gz \
    data/packrun.db data/packrun.db-wal data/packrun.db-shm \
    data/packages configs/config.yaml

# 3. 另行保管：/etc/packrun.env、file: 引用的 SSH 私钥（数据库里只有引用，没有明文）
```

local 模式如需保留部署现场，追加 `data/sandbox`。

### 10.2 在线备份（不停车）

`packrund backup` 用 SQLite `VACUUM INTO` 生成一致性快照，校验 `integrity_check` 与
SHA256 后，连同 `packages/` 一起写入输出目录，并写一份 `manifest.json`。**不需要停服务**：

```bash
cd /opt/packrun/server
./packrund backup -config configs/config.yaml -out /backup -keep 7
# 备份完成: /backup/20261118-193000
```

输出目录结构：

```
/backup/20261118-193000/
├── manifest.json          # createdAt、库文件 SHA256/字节数、包文件数与总字节
├── packrun.db             # VACUUM INTO 生成的一致快照，可直接替换主库
└── packages/              # 与快照同代次的包仓库副本
```

`-keep 7` 表示只保留最近 7 份（按目录名排序），更早的自动删除。定时任务用仓库自带的
`deploy/packrun-backup.sh` 包装：

```bash
# /etc/cron.d/packrun-backup
30 3 * * * root PACKRUN_BIN=/opt/packrun/server/packrund \
  PACKRUN_CONFIG=/opt/packrun/server/configs/config.yaml \
  PACKRUN_BACKUP_DIR=/backup PACKRUN_BACKUP_KEEP=7 \
  /opt/packrun/server/deploy/packrun-backup.sh
```

脚本会校验二进制、配置文件与输出目录是否可用，任一不满足直接非零退出，
便于 cron 告警；成功时把 `备份完成: <dir>` 打到 stdout。

> 备份期间数据库仍可读写，但 `VACUUM INTO` 会占用一份与库等大的临时空间；
> 包仓库副本按实际体积占用磁盘，请把 `-keep` 与磁盘容量一起规划。
> 备份目录不允许位于 `storage.package_dir` 内部，否则会被拒绝（避免自我复制）。

### 10.3 恢复

1. 停止服务；2. 用同一份备份里的 `packrun.db` 与 `packages/` 一起覆盖
（**不要**把旧 WAL/SHM 套到新主库上，恢复后可只保留 `packrun.db`）；
3. 恢复 env 与私钥；4. 启动并按 §9 验收。
需要核对备份是否完整时，先看 `manifest.json` 里的 `databaseSha256` 与
`packageFiles`，再用 `sqlite3 <db> "PRAGMA integrity_check;"` 复核。

### 10.4 澄清：部署备份 ≠ 数据备份

部署时产生的 `<目录>.bak-YYYYmmddHHMMSS`（local 改名 / SSH `cp -a`）只是**应用旧版本**，
且部署成功后按 `keepReleases` 自动清理。部署失败时系统会**自动用该备份恢复部署前版本**
（见 §17），因此 `.bak-*` 是回滚现场的一部分，不要手工删除正在被引用的备份。
项目「回滚」是另一条链路：用包仓库中的历史安装包重新发布，与 `.bak-*` 无关。

### 10.5 包仓库回收（GC）

安装包被任务引用过之后就不再按「3 天上传保留」清理，若不回收，包仓库会在若干个月后吃满
`storage.max_total_mb`，届时**所有上传都会返回 507**。系统内置按版本窗口的回收：

| 规则 | 说明 |
|---|---|
| 每个目录保留最近 N 版 | 按任务倒序取每个 `directory_id` 最近 `package_keep_releases`（默认 10）个不同版本的包 |
| 最近上传一律保留 | `package_keep_days`（默认 7）天内上传的包不动，避免刚上传还没发布就被回收 |
| 未引用上传 3 天清理 | 从未被任何任务引用、且超过 3 天的上传记录直接清理（原有行为） |

后台每小时执行一次维护，包仓库回收**每天执行一次**。先看清单再动手：

```bash
cd /opt/packrun/server
./packrund gc                      # dry-run：只打印将回收的包与原因
./packrund gc -apply               # 真正删除文件与记录
./packrund gc -keep 20 -keep-days 14 -apply   # 临时放宽窗口
```

> **回滚窗口是有代价的**：超出窗口的包被回收后，对应批次无法再回滚，
> 任务详情里点「回滚」会提示安装包已被回收。需要长期保留的版本请调大
> `package_keep_releases`，或把包另行归档（GC 不碰 `data/packages` 之外的文件）。

## 11. 升级流程

1. 选无任务窗口（重启会把未完成任务标记失败）。
2. 按 §10 完成备份。
3. 在仓库根目录执行 `make build` 生成新的单文件二进制；`systemctl stop packrund`
   后替换二进制（前端已内嵌，无需再同步静态文件）。
4. 启动：GORM 每次启动直接 `AutoMigrate`，**没有独立迁移命令、没有降级流程**——升级前备份是唯一回退手段。
5. 检查启动日志中的 `[recover]` 行（被中断任务数量），并人工核对上次中断任务的目标机
   目录是否残留半成品（数据库标记失败不代表目标机已恢复原状）。
6. 按 §9 重新验收；替换二进制后强制刷新浏览器（静态资源带 hash，正常无缓存问题）。
7. 升级依赖后复跑漏洞扫描：

   ```bash
   cd server && go run golang.org/x/vuln/cmd/govulncheck@latest ./...
   cd web && pnpm audit --prod
   ```

8. 更换 `PACKRUN_JWT_SECRET` 会使所有已登录会话失效（用户需重新登录）。

## 12. 安全加固清单

- [ ] `server.mode: release`；`PACKRUN_JWT_SECRET` ≥32 字节随机值；`PACKRUN_ADMIN_PASSWORD` 强口令
- [ ] 首次登录立即改密、绑定 TOTP、离线保存 10 枚恢复码
- [ ] `deploy.mode: ssh`；未设置 `PACKRUN_SSH_INSECURE`；目标机指纹已登记（TOFU 自动登记，或在服务器管理中确认指纹）
- [ ] 直连时安全组/防火墙限制 9000 来源；使用 Nginx/frp 时 `server.addr` 改为 `127.0.0.1:9000`，frps `proxyBindAddr=127.0.0.1`，18080/9000 不对公网开放

- [ ] 使用「直接录入」凭据时：`PACKRUN_CREDENTIAL_KEY`（≥32 字符随机值）与数据库分离存放；更换主密钥后需在服务器管理中重新录入凭据

## 13. 角色与权限

| 角色 | 侧边栏菜单 | 能力 |
|---|---|---|
| **管理员 admin** | 概览、项目工作台、服务器、部署向导、任务、脚本、审计日志、用户与权限 | 全部配置（服务器/目录/脚本/用户/项目）、发布、审计 |
| **发布者 deployer** | 概览、项目工作台、服务器、部署向导、任务、脚本 | 在其 `serverScope` 内上传、部署、发布项目、取消任务 |
| **审计员 auditor** | 概览、服务器、任务、脚本、审计日志 | 只读查看与审计；不能上传、部署、发布、取消、改配置 |

补充规则：

- `serverScope` 控制非管理员可见/可操作的服务器集合（`*` 或空 = 全部，否则为服务器 ID 列表；
  当前用户界面下拉只支持「全部」或单台）。范围外的目录、任务、概览数据一律隔离。
- 非管理员看到的服务器凭据引用一律脱敏为 `***`，仅管理员可见原始引用。
- 例外：审计员可以点「检测」做连通性测试（接口在普通认证路由下）——这是当前实现的
  事实行为，如不接受请勿给关键账号 auditor 角色。
- 生产环境（服务器 `env=prod`）发起部署/发布/回滚必须输入动态口令（TOTP step-up），
  由**目标服务器环境**决定，与登录账号、服务运行模式无关。

## 14. 首次登录与安全加固

1. 用初始管理员账号登录（release 模式密码为 `PACKRUN_ADMIN_PASSWORD` 注入值；
   debug 模式默认 `admin / Admin@12345`）。
2. **改密**：右上角头像 → 个人设置 → 修改口令。新口令 ≥8 位；已绑 TOTP 时还需动态口令。
   改密成功后**所有会话立即失效**（含当前浏览器），需重新登录。
3. **绑定动态口令**：个人设置 → 动态口令 → 「生成绑定种子」→ 在认证器 App（Google
   Authenticator / 1Password 等）中**扫描页面二维码**（无法扫码时手动录入种子，参数
   SHA1/6 位/30 秒）→ 输入 6 位码完成绑定。
4. **保存恢复码**：绑定成功弹出 10 枚一次性恢复码，**仅展示一次**，立即复制离线保存。
   认证器不可用时可在登录页用恢复码替代动态口令（去连字符后 16 位，每枚仅一次）。
   恢复码只用于登录，不能替代部署 step-up、换绑、改密所需的动态口令。

登录失败 5 次（同账号）或 30 次（同 IP）锁定 5 分钟；未输入动态口令的尝试也计入失败。

## 15. 管理员准备：服务器、目录与脚本

发布前置数据由管理员配置，发布者只消费。

### 15.1 新增服务器

服务器 → 新增服务器：

| 字段 | 说明 |
|---|---|
| 名称 | 仅字母、数字、点、下划线、连字符 |
| 环境 | `prod` / `test` / `dev`；**prod 会被前端红框提示，且发布强制 TOTP** |
| 主机 / 端口 / SSH 用户 | 中控机必须能直连该 SSH 端口 |
| 认证方式与凭据 | 三种方式任选：① **直接录入**——表单里直接填密码/私钥，AES-256-GCM 加密入库（需配置主密钥 `security.credential_key` 或环境变量 `PACKRUN_CREDENTIAL_KEY`，≥32 字符；密钥不落库，换钥后需重新录入）；② `file:~/.ssh/id_ed25519`（`~` 按 packrund 运行账号 home 解析）；③ `env:PROD_SSH_PASSWORD`。私钥不能带 passphrase（无交互输入流程） |
| 并发上限 | 该服务器同时执行任务数，与全局并发叠加生效 |

点「检测」连接目标机并采集一次运行指标（负载/内存/磁盘/系统信息/运行时长），
同时做凭据自检（引用能否解析、内置凭据能否解密、私钥是否带 passphrase），失败时给出明确原因。
首次连接成功时自动登记主机指纹（TOFU，写审计日志 `server.hostkey.autotrust`），
之后每次连接据此校验，指纹不匹配即拒绝——服务器重建后请在「服务器 → 指纹」中
清除重新信任。关闭 `auto_trust_hostkey` 时回退中控机 `~/.ssh/known_hosts` 校验。
local 模式恒返回成功，**不代表**主机可达。

服务器列表的状态列常驻负载/内存/磁盘摘要，展开行可看完整指标；后台按
`deploy.metrics_interval_seconds`（默认 300 秒，0 关闭）定时采集，「概览」页有
各服务器资源汇总。

### 15.2 配置部署目录

服务器卡片 → 目录 → 新增：

- **路径**：强制绝对路径，拒绝 `/` 与 `..`；
- **属主**：仅作为记录保存，系统不会自动 chown——目标机目录权限需事先就绪；
- **覆盖策略**：`允许覆盖` / `仅新增`。注意「仅新增」**只对 jar 单文件生效**，
  zip 部署始终覆盖同名文件（见 §21）；
- **备份**：部署前备份 + 保留份数 `keepReleases`（0 = 不保留，成功后清理全部 `.bak-*`）；
- **空间阈值 `maxSizeMB`**：部署前校验目录占用，解压时按实际字节校验，超出即失败。

### 15.3 脚本（可选）

脚本 → 新增脚本：

- **阶段**：`precheck`（解包前执行，失败即终止、不覆盖现有版本）/ `postdeploy`（部署后执行）；
- **执行身份 runAs**：ssh 模式下与 SSH 登录用户不同时用 `sudo -n -u <用户>` 执行，
  需目标机配置免密 sudo，否则脚本失败；
- **超时**：1–3600 秒，默认 120 秒；
- 编辑保存会递增版本号，任务会记录所用脚本版本。

脚本内容在目标目录中以 `sh` 执行；目标机需有 `base64`、`timeout` 命令。
local 模式下脚本只渲染回显，**不会真实执行**。

> 运维提醒：排队中的任务在**执行时**才读取脚本当前内容——不要编辑已被排队任务
> 引用的脚本，否则实际执行版本与任务记录的版本可能不一致。

### 15.4 SSH 目标机依赖清单

无需安装任何 agent，但目标机的 SSH shell 必须具备：

| 用途 | 命令 |
|---|---|
| 基础部署 | `sh` `cat` `mkdir` `sha256sum` `rm`；jar 部署另需 `mv` |
| 容量/备份/清理 | `du` `cut` `ls` `cp` `tail` `rm -rf` |
| zip 部署 | `unzip` `zipinfo` `wc` `grep`（缺 `zipinfo` 会直接拒绝 zip 部署） |
| 脚本执行 | `base64` `timeout`；跨用户执行另需免密 `sudo` |

并保证：SSH 账号可写 `/tmp` 与目标目录（含创建 `.bak-*` 备份）、可删除旧备份。

## 16. 用户管理

管理员 → 用户与权限：

- **新增用户**：账号、显示名、初始口令（≥8 位）、角色、归属主账号、数据范围；
  用户名创建后不可改。
- **编辑**：显示名、角色、数据范围、状态；可重置口令。改动会使该用户所有旧会话失效。
- **归属主账号**：可选择，也可清空（下拉框清空即解除归属，后端写 NULL）。只允许一层归属，
  不能指向自己或挂到子账号下。它只是组织层级展示，**不等于**项目授权；
  项目可见性由项目成员关系决定（§18）。
- **删除账号**：软删除——账号立即下线、从列表消失、会话失效，但历史任务与审计记录里
  的操作人字符串保留。以下情况会被拒绝：删除自己、仍是项目创建者、还有未完成任务、
  是最后一个启用管理员。删除后账号名释放，可重建同名账号。
- **重置动态口令**：管理员可在用户行点「重置口令」，清除该账号的 TOTP 种子与全部恢复码，
  并使其在线会话失效；之后由用户自己重新扫码绑定。该操作写 `user.otp.reset` 审计。
- **禁用**：禁止禁用/降级最后一个启用状态的管理员。

## 17. 部署向导（单目标发布）

部署向导 → 三步：

1. **选择目标**：点选服务器 → 选该服务器的部署目录（展示覆盖/备份/空间阈值策略）。
2. **上传安装包**：拖拽或点选 `.zip` / `.jar`（≤200MB，前端先校验，后端再校验文件头）；
   或从最近上传列表选择已有包（页面展示前 8 条）。**安装包按上传者隔离**：发布者只能看到、
   只能使用自己上传的包；管理员与审计员可见全部。用别人的包发起任务会返回 403
   「只能使用自己上传的安装包」。
3. **脚本与确认**：可选一个前置脚本、一个后置脚本，核对摘要；**目标为 prod 时页面内
   输入当前 6 位动态口令** → 「确认并执行」。

提交后自动跳转任务详情，运行中每 2 秒轮询；任务状态机：
`pending → uploading → verifying → executing → success / failed / canceled`。

执行流程（ssh 模式）：前置脚本 → 上传到目标机 `/tmp` → `sha256sum` 二次校验 →
zip 用 `zipinfo` 做路径穿越/软链审查后 `unzip`（jar 用 `mv`）→ 后置脚本 → 按
`keepReleases` 清理旧备份。

**任一步失败任务即失败，并自动用本次部署前的备份恢复目标目录**：定位到失败后
系统把当前目录改名保留为 `<目录>.failed-<时间戳>`，再把 `<目录>.bak-*` 换回原路径，
恢复成功后删除 `.failed-*`；动作会写进任务日志（「部署失败，正在恢复部署前版本…」
「已自动恢复部署前版本」）。若恢复本身失败，任务错误信息追加
「；自动恢复失败：<原因>（备份保留在 <路径>）」，失败现场与备份都保留，按这两个路径人工处理。
任务失败后可修正原因直接重发。

单用户同时排队/执行中的任务上限 10（`deploy.max_pending_per_user`）；同一部署目录的任务强制串行。

## 18. 项目工作台（批量发布与回滚）

以「项目」为中心：绑定多个更新目录，拖包一键发布到全部绑定目录，按批次管理历史与回滚。

### 18.1 权限模型

- **Owner（创建者）**：项目创建时自动成为隐式成员，列表、详情、发布历史均可见，
  可发布与回滚；项目设置页的成员列表会把 Owner 置顶展示，且不可被移除。
- **成员**：管理员在「项目设置 → 成员」里勾选，成员同样具备发布与回滚权限。
- **管理员**：可见全部项目，不受成员关系限制。
- 非 Owner、非成员、非管理员的发布者既看不到该项目，也无法对其发起发布/回滚（403）。

> 成员下拉只列非管理员账号；如果历史项目里有已被删除的用户，下拉会用项目成员数据兜底
> 展示，不会退化成裸 ID。

### 18.2 发布流程

1. 项目工作台 → 新建项目（名称、可选标识与描述）。
2. 项目设置 → 绑定更新目录（可跨服务器多选）；管理员可同时设置成员与发布策略
   （发布前备份/保留版本数——该策略会**同步改写全部绑定目录的全局目录策略**，不只影响本项目）。
3. 部署空间拖入 zip/jar 或选择最近上传的包 → 「发布项目」。
4. 绑定目录中含 prod 时输入一次动态口令。
5. 系统为**每个绑定目录各创建一条任务**组成批次；发布历史页 1.5 秒轮询批次状态。

### 18.3 版本与回滚规则

- 项目版本从 `v0.0.0` 起，每次成功发布 patch +1（如 `v0.0.2 → v0.0.3`），无手工版本号。
- **批次内全部任务成功**版本号才推进；部分失败不推进版本。失败的目标会各自自动恢复
  部署前版本（§17），已成功的目标保持新版本，需人工核对整体一致性。
- 同一项目存在运行中批次时，禁止再次发布或回滚。
- **回滚**：发布历史中点选一条「成功」记录（不能是当前版本）→「回滚到此版本」→
  确认（prod 需 TOTP）→ 生成一组新的 `rollback` 任务。语义是**用该批次的历史安装包，
  对项目当前绑定的全部目录重新部署一遍**——不是恢复文件系统备份，也不保证恢复到
  原批次的目标集合。**删除或清理历史包后对应版本将无法回滚**（包仓库无删除界面，
  人工清理文件前务必确认不再需要回滚）。
- 项目发布不会自动执行前置/后置脚本（界面未提供脚本选择；向导单目标发布才可选脚本）。
- 批次没有「一键取消」，需到任务详情逐条取消。

## 19. 任务管理与日志

- 任务页：按任务号/包名/操作人搜索、按状态筛选、分页；列表需手动刷新。
- 任务详情：目标、包、SHA256、脚本版本、OTP 校验状态、步骤时间线与**逐步日志**、
  失败原因；运行中 2 秒轮询，终态停止。
- **取消**：非审计员可取消其 `serverScope` 内任何未结束任务（不限于本人创建）；
  排队任务直接标记取消，执行中任务发取消信号。执行中的任务被取消后会**尝试恢复
  部署前版本**（与失败同样的逻辑），恢复失败时按任务日志里的路径人工处理。
- 无 WebSocket 日志流、无日志导出；跨页分析需用审计日志或自行对接数据库备份。

## 20. 审计日志与个人设置

### 20.1 审计日志（admin / auditor）

- 筛选：动作、操作人；搜索：对象或任务号；分页 20/50/100。
- 记录字段：时间、操作者、动作、对象、结果、动态口令校验状态、来源 IP、详情、任务号。
- 登录、配置变更、任务创建与终态、服务重启恢复（`task.recover`）、项目事件全部落审计。
- 当前无导出与时间范围控件；项目相关动作（`project.*`）会以原始 action 展示，
  但不在动作下拉预设里，直接搜索对象关键字更方便。

### 20.2 个人设置

- 账号信息只读展示（账号、显示名、角色、数据范围、最近登录）。
- **换绑 TOTP**：输入当前动态口令 → 录入新种子 → 新码确认；确认前旧认证器仍有效，
  完成后重新生成恢复码（旧码作废）。
- **解绑 TOTP**：当前动态口令 + 二次确认；解绑后清空恢复码，且无法再发起生产部署。
- **重新生成恢复码**：需当前动态口令，旧码立即全部失效。
- **修改口令**：原口令 + 新口令（≥8 位）；已绑 TOTP 时还需动态口令。成功后全部会话失效。
- 同一 TOTP 时间片内的码成功使用一次后不可重放——连续两次敏感操作时需等认证器刷新下一个码。

# 第三部分 已知限制与常见问题

## 21. 已知限制

以下为当前代码的真实行为，使用与排障时不要按「想当然」的语义理解界面文案：

| # | 限制 | 说明 |
|---|---|---|
| 1 | zip 部署不受「仅新增/禁止覆盖」约束 | 该开关只对 jar 单文件生效；zip 在 ssh 模式用 `unzip -o` 覆盖同名文件（但**不删除**目录中多余的旧文件），local 模式截断同名文件。需要干净替换的目录请用脚本自行处理 |
| 2 | 项目回滚依赖历史包文件 | 包仓库无删除/GC 接口；人工清理 `data/packages` 会使相关版本无法回滚 |
| 3 | 自动恢复只覆盖「目标目录」 | 失败后恢复的是部署目录本身；脚本产生的副作用（重启服务、写 `/etc`、建软链）不会被撤销，需脚本自身可重入 |
| 4 | 上传重试可能留下重复包记录 | 响应丢失时前端自动重试，服务端已登记的记录会重复一条；未被任务引用的上传记录 3 天后自动清理，也可在「最近上传」里手工删除 |
| 5 | 健康检查不探测目标机 | `/healthz` 只检查本机数据库、包目录与磁盘；SSH 凭据与目标机连通性仍以「服务器 → 检测」为准 |
| 6 | 重启即弃任务 | 所有未完成任务重启后标记失败，不续跑；`task.recover` 审计可查 |
| 7 | 排队任务执行的是脚本最新内容 | 执行时按脚本 ID 重读记录；不要编辑已排队任务引用的脚本 |
| 8 | local 模式的「检测/部署成功」无目标机语义 | 检测恒成功；脚本只回显；不能验证脚本语法、systemd、目标机依赖 |
| 9 | 部署目录「属主」字段不生效 | 不会自动 chown，目标机权限需事先就绪 |
| 10 | 项目发布策略影响全局目录策略 | 设置页改「备份/保留版本数」会改写全部绑定目录的目录配置本身 |
| 11 | 审计员可执行连通性检测 | ping 在普通认证路由下且会更新服务器状态 |
| 12 | 单步日志有上限 | 头部 8KB + 尾部 24KB，中间丢弃并标注省略量；需要完整输出请让脚本自行落盘到目标机 |
| 13 | 告警去重依赖进程内存 | 重启后同一失败任务或证书可能重复告警一次；跨重启不保证只报一次 |
| 14 | 历史版本包会被回收 | 超出 `package_keep_releases` 窗口的安装包每天回收一次，被回收批次的「回滚」会失败并提示包已回收；需要长期保留请调大窗口或另行归档 |
| 15 | 审计与任务按保留期删除 | 默认 180 天（`storage.audit_retention_days` / `storage.task_retention_days`），`0` 可关闭；合规要求更久时先导出再调大 |

## 22. 常见问题排查

**Q：release 模式启动直接退出，日志「配置安全校验失败」？**
对照 §5：JWT 密钥缺失/过短/等于 dev 默认值、管理员口令用了 `Admin@12345`、
`allowed_origins` 含 `*`、ssh 模式带 `PACKRUN_SSH_INSECURE=1`，任一项都会拒启。

**Q：登录页反复提示失败，但密码正确？**
账号已绑 TOTP：首次提交不带动态口令也会计入失败次数；确认输入当前 6 位码或改用恢复码。
同账号 5 次失败锁 5 分钟，等待即可。

**Q：创建 prod 任务返回 1428？**
step-up 再认证失败/缺失：在向导确认步骤输入认证器当前 6 位动态口令；同一码不可重放，
连续操作等下一个码。

**Q：/healthz 返回 503 / degraded？**
看 `checks` 里哪一项是 `fail`：`database` → 库损坏（`PRAGMA integrity_check` 复核）或库目录不可写；
`packageDir` → 目录权限不对、磁盘只读；`disk` → 剩余空间低于 `alert.disk_min_free_mb`。
`warn` 项（配额接近上限、最近有失败任务）不影响 200 状态码。

**Q：上传 413 / 上传中途断开？**
413 有两种来源：Nginx `client_max_body_size`（按 §14 用 `210m`）与服务端 200MB 上限
（返回 JSON「包大小超过上限 200 MB」）。中途断开：服务端不会留下半截包，前端会自动
重试一次；仍失败就换稳定网络，或把包拆小（弱网 + 200MB 需要十几分钟）。

**Q：SSH 部署失败「host key 未登记 / 拒绝连接」？**
到「服务器」页对目标机点一次「检测」：首次连接成功即自动登记指纹（TOFU），
无需再手工 `ssh-keyscan`。若报「主机指纹不匹配」，说明目标机指纹与登记值不一致
（服务器重建或中间人风险）：确认服务器确已重建后，在「服务器 → 指纹」中清除并重新检测。
关闭 `auto_trust_hostkey` 的存量环境仍走 packrund 运行账号的 `~/.ssh/known_hosts`。
仅 debug 环境可临时 `PACKRUN_SSH_INSECURE=1`，release 下设置会拒启。

**Q：报「内置凭据无法解密 / 非 debug 模式必须配置非默认的 credential_key」？**
「直接录入」的凭据用主密钥加密存放：release 环境必须通过 `security.credential_key`
或 `PACKRUN_CREDENTIAL_KEY` 配置 ≥32 字符的非默认短语（数据库不存密钥）。若曾更换
主密钥，旧密文无法解密——检测自检会明确提示，到服务器管理重新录入该服务器的凭据即可。

**Q：zip 部署在目标机报 `zipinfo: command not found`？**
安装 `unzip` 包（提供 unzip 与 zipinfo）。安全审查强依赖 zipinfo，无法绕过。

**Q：脚本执行失败提示 sudo？**
`runAs` 与 SSH 登录用户不同时需要目标机 `sudo -n -u <用户>` 免密执行；
为部署账号配置受限 sudoers，或改用与目录属主一致的 SSH 账号。

**Q：项目列表里看不到我（发布者）刚建的项目？**
已知缺陷 §21.2：用管理员创建项目并把该发布者加入成员。

**Q：回滚按钮置灰 / 回滚失败？**
只能选「成功」且非当前版本的历史；确认历史批次所用安装包仍在包仓库
（`data/packages` 未被清理）；确认项目当前没有运行中的批次。

**Q：服务重启后一堆任务变「失败」？**
设计如此（§21.8）：检查启动日志 `[recover]` 行，人工核对目标机目录是否残留半成品后重发。

**Q：`PACKRUN_ADMIN_PASSWORD` 改了为什么管理员密码没变？**
该变量只在**空库首次初始化**时生效。忘记密码需数据库运维介入（重置 `users` 表中
对应记录的口令哈希），没有自助重置接口。

**Q：审计日志里的 IP 是 127.0.0.1？**
`trusted_proxies` 配置与拓扑不符（§7.2）。仅回环代理链路才保留默认值；
否则要么清空，要么修正代理层 XFF 写入。
